Process

The judgment calls behind the work — not just the finished result.

Judgment in practice

Rejecting the obvious choice

When building this site's visual identity, I generated a network/node-graph texture as the hero graphic — the default "AI" visual. I rejected it: it's become a design cliché that suggests "artificial intelligence" generically rather than communicating anything about my actual work, and its density fought the calm, understated mood the rest of the kit is built around. I used a single trend-line graphic instead — it echoes the actual signal (search performance trend) the capstone is scoring.

Choosing the boring stack on purpose

For this site itself, I compared three build options — plain HTML + GitHub Pages, Jekyll, and React + Vercel with a live model demo — before choosing the simplest one. The more powerful option could have shown a live, interactive demo of the model, which was genuinely tempting. I didn't have a trained model to demo yet, so I chose not to build complexity in service of a capability I didn't actually have.

Reading my own model's mistakes out loud

The capstone case study includes real false positives and false negatives from the Random Forest model — not because they're impressive, but because they show where the model's assumptions break. Low-volume pages get flagged as "declining" when they may simply not have enough traffic for a trend to register either way; freshly-updated pages get missed because the model treats recency as a stand-in for "healthy" that doesn't always hold.

Tools & workflow

I use a Claude Project configured with my Voice Card (practical, clear, honest, curious, evidence-based) as a standing instruction, so AI-assisted drafts already sound like me before I edit them, not after. My identity kit's style note lives there too, so new pages and visuals inherit it automatically instead of me re-specifying it each time.

For recurring research tasks, I use a four-step chained workflow (Gather → Synthesize → Draft → Review & Format) rather than one long prompt — narrow, single-purpose steps are easier to check and catch mistakes in than one prompt trying to do everything at once.
